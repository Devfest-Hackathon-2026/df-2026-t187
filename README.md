# yukid-df-hack｜粗悪なアプリの改修を通じてプロダクト思考を学ぶ開発スタジオ基盤

意図的に使いにくく作られたアプリを題材に、コード構文を直接書かずに、誰のために・何を優先し・何を捨てるかというプロダクトの意思決定サイクルを体験・検証するための開発スタジオ基盤です。

本リポジトリは、チーム内ハッカソンなどで他の開発者がベースとしてフォーク・改造することを前提に設計されています。改修対象となるアプリの初期仕様・顧客層・ペルソナの行動制約・UIコンポーネントはデータ駆動で分離されており、テーマを自在に差し替えて新しい課題アプリや評価環境を構築できます。

## コアとなる6段階の体験ループ

1. **顧客層を選ぶ**
   - 定義された複数の顧客層から、誰のために改善するかを理由とともに選択します。選択した顧客層に属するペルソナがレビュー担当として割り当てられます。
2. **ダメ出し**
   - スマートフォン実機プレビューの気になる部品を赤ペンで囲み、問題点や疑問を自然言語で送信します。
   - 赤ペンの軌跡座標とUI部品の矩形座標から対象コンポーネントを特定し、スクリーンショット画像とともにマルチモーダル入力としてAIへ渡します。
3. **議論**
   - 議論AIは直接コードを書かず、メリットと副作用が異なる複数の改善方針を提示して問い返します。
   - 人間がどの方針を採るかを理由とともに選ぶと、Gemini Function Calling を通じて判断履歴が記録されます。
4. **改修**
   - 実装AIがアプリの見た目と状態遷移ロジックを更新します。
   - 生成されたアプリ仕様は単一HTMLサンドボックスとしてレンダリング検証およびタスク完了イベントの到達検査を行い、破損時は直前のチェックポイントへ自動ロールバックします。
5. **レビュー**
   - レビューAIはこれまでの議論や改修意図を共有されない状態で、画面を実際に操作します。
   - ペルソナごとに設定された視界のぼかし・コントラスト低下・タップ位置のブレ・最大手数・許容待ち時間などの数値制約のもとでシミュレーションを実行し、タスク完了イベントの発火有無によってコード側が達成か離脱かを判定します。
   - Gemini は操作ログに基づく各ペルソナの感想生成のみを担い、改善方法は指示しません。生成された感想は音声読み上げで再生できます。
6. **採否を決める**
   - 各ペルソナからのフィードバックに対して、人間が直す・反論して残す・保留の採否と理由を決定し、次の改善サイクルへ進みます。

## 3つのAIの役割分担

| 役割 | 入力 | 出力と制約 |
| :--- | :--- | :--- |
| **議論AI** | 現在のアプリ仕様・赤ペン囲み画像・対象部品ID・対話履歴 | トレードオフの異なる改善案の提示、または部品の仕組み解説。直接コードは書かない |
| **実装AI** | 選択された改善案・人間の判断理由・現在のアプリ仕様 | 更新後のUIと状態遷移ロジックを含むアプリ仕様のJSON生成およびサンドボックス検証 |
| **レビューAI** | 画面状態・制約変数下で実行した操作ログ。議論履歴は非共有 | タスク完了イベントに基づく達成・離脱判定と、ペルソナごとの感想生成 |

## ハッカソンでの拡張・カスタマイズ箇所

初期状態ではサンプルテーマとして使いにくいアプリと複数の顧客層が定義されていますが、以下のモジュールを編集することで任意のアプリ・顧客像・評価ルールに差し替えられます。

- [`src/shared/initialTheme.ts`](src/shared/initialTheme.ts)：改修対象となる初期アプリの仕様、顧客層、各ペルソナのプロフィールと行動制約パラメータの定義
- [`src/shared/types.ts`](src/shared/types.ts)：サンドボックス内で扱えるUI部品種別、インタラクション挙動、アクションの型定義
- [`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts)：スマホ画面内でのコンポーネント描画とイベント発火ロジック
- [`src/shared/sandboxValidator.ts`](src/shared/sandboxValidator.ts)：単一HTMLサンドボックスの整合性検査と、ペルソナ制約下での操作シミュレーション判定ロジック
- [`src/server/gemini.ts`](src/server/gemini.ts)：3つのAIのプロンプト設計、Structured Outputs スキーマ、およびAPIキー未設定時のフォールバック推論ロジック

## 技術構成

- **フロントエンド**：TypeScript / Vite / HTML5 Canvas / Sandbox `iframe`
- **バックエンド**：Node.js HTTP Server / `@google/genai` によるマルチモーダル入力・Structured Outputs・Function Calling
- **インフラ・永続化**：Google Cloud Run / Cloud Firestore / Firebase App Check
- **品質・衛生管理**：Node.js Test Runner / `scripts/check-hygiene.mjs` によるコミット・機密情報・パス混入検査

## セットアップ・起動方法

### 1. パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

`.env.example` を `.env.local` にコピーし、Gemini API キーまたは Google Cloud プロジェクトを設定します。未設定の場合でも内蔵のフォールバックエンジンで全ステップの動作を確認できます。

```bash
cp .env.example .env.local
```

```env
GEMINI_API_KEY=your_gemini_api_key
```

### 3. 開発サーバーの起動

```bash
npm run dev
```

ブラウザで `http://localhost:5173` を開くとスタジオ画面が表示されます。

### 4. テスト・ビルド・衛生チェック

```bash
npm test              # ユニットテスト・コミット衛生テストの実行
npm run typecheck     # TypeScript 型チェック
npm run build         # 本番ビルド
npm run check:hygiene # 機密情報・ローカルパス混入・コミット規約チェック
```
