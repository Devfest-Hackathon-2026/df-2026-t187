# yukid-df-hack｜粗悪なアプリの改修を通じてプロダクト思考を学ぶ開発スタジオ基盤

意図的に使いにくく作られたアプリを題材に、コード構文を直接書かずに、誰のために・何を優先し・何を捨てるかというプロダクトの意思決定サイクルを体験・検証するための開発スタジオ基盤です。

## コンセプト・背景

- **「プログラム構造の学習」と「プロダクト設計の学習」の分離**
  - Scratch や基本構文の学習が「プログラムの構造や仕組み（How）」を学ぶ場であるのに対し、本スタジオは「売り手（ビジネス目標・売上）と顧客（多様なニーズ・制約）の間でプロダクトをどう成立させるか（What / Why）」を学ぶ場として設計されています。
  - 生成AIの普及により「一応動く画面を作る」ハードルが下がったからこそ、入り口の段階で「ターゲットを決め、手直しし、顧客の反応や売上が変わる手応え（Why）」を先に体験し、そこから裏側の仕組み（How）への学習動機につなげます。
- **個人開発では得にくい「多面的なレビューとトレードオフ」の検証環境**
  - プロダクトを成立させるには、ターゲットを設定して作り、多様な顧客からのレビューとビジネス成果の両面を見て改善を回すサイクルが不可欠ですが、個人開発や独学でその環境を用意することは困難です。
  - 本スタジオは、依頼主（店長）と、異なる目的・身体制約・要望を持つ顧客ペルソナ（3客層×3人）の実操作シミュレーションを備え、1人でもプロダクト改善のコアループを反復できる環境を提供します。

本リポジトリは、チーム内ハッカソンなどで他の開発者がベースとしてフォーク・改造することを前提に設計されています。改修対象となるアプリの初期仕様・顧客層・ペルソナの行動制約・妨害要素は題材ファイル1つにまとまっており、操作シミュレーターは部品の役割だけを見て判定するため、題材を差し替えて新しい課題アプリや評価環境を構築できます。

## サンプル題材：コーヒー豆の通販画面

初期状態では、商品の説明と注文フォームが1ページにまとまった単品通販の購入画面を題材にしています。

- **固定の問題「売上を伸ばしたい店長が付け足した画面」から始まります。** 反応しない注文ボタン、点滅しながら減っては2:59に戻る偽の「残り2:59で売り切れ」、光る「今すぐ購入」のおとり、数秒後に出るクーポン広告、最初からチェックの入った定期便の5つが入っています。
  - まず反応しない注文ボタンを直すことで「0件だった注文が入るようになる」という最初の成功体験が得られ、同時に定期便の罠や広告による「不満」「後悔」が表面化します。
  - 定期便やクーポン広告は、初期の見せ方が悪質なだけで、機能そのもの（毎月届く便利さ・割引のお得さ）を求めているお客さんもいます。そのため、ただ削除すると誤申込の後悔はなくなる一方で、それらを望んでいたお客さんが「毎月届けてほしいのに設定がなくて残念」「クーポンを使いたかったのに無くなってしまったのか」と不満を抱き、店長も売上減を嘆きます。
  - 最初からOFFで条件が読める正直な定期便や、押しやすい閉じるボタン・画面内バナーへ**「使いやすい形に整えて残す」**ことで初めて、選んだ3人全員の満足と店長の売上目標が両立します。
- **依頼主の店長が登場します。** 冒頭で事情を話し、「どんなお客さんを一番大事にするか」を尋ねます。改造するたびに売上の立場から一言反応し、お客さんの反応を見るたびに注文数や定期便の件数をコードで数えて反応するので、お客さんとお店の板挟みを体験できます。
- **顧客層は「購入画面で何を求めているか」で分けています。** さっと買いたい人・確実に買いたい人・損をしたくない人の3つで、求めることがぶつかり合うため、誰を選ぶかが何を優先するかの判断になります。目が遠い・指が震える・細かい字を読む・定期便やクーポンを使いたいといった違いは、各人の制約として持たせています。
- 練習用に、妨害要素の組み合わせを毎回ランダムにするモードもあります。妨害要素は、毎回必ず入るもの・現実の使いにくさ・冗談の3種類から選ばれ、壊れ方の多さを3段階から選べます。

| 難しさ | 妨害要素の数 | 冗談 | 向いている場面 |
| :--- | :--- | :--- | :--- |
| easy | 2〜3個 | なし | 初めての人、短い時間の体験会 |
| normal | 3〜5個 | 0〜1個 | 標準 |
| hard | 8〜9個 | 2個 | 慣れたチーム、何を捨てるかを強く迫りたいとき |

## 体験の流れ

1. **顧客層を選ぶ**
   - 依頼主の店長が事情を話したあと、システムメッセージで「誰のために手直ししますか」と尋ねます。選んだ顧客層の3人（例：目が遠いお客さん・指が震えるお客さん・スマホに不慣れなお客さん）が来店し、それぞれの希望を話します。
2. **ダメ出しと質問・対話**
   - スマートフォン実機プレビューの気になる部品を赤ペンで囲むか、チャット入力欄から自然言語で送信します（マイク音声入力にも対応）。
   - 宛先ピル（`お助けAI`・`店長`・`お客さん` の3択、または `@店長` `お客さん、` などの呼びかけ）で直接質問・相談できます。`お客さん` に質問すると、3人がそれぞれの立場から順番に一言ずつ返答します。
   - 質問にはお助けAIが画面の実際の仕様にある事実だけで短く答え、誰が喜ぶか・困るかといった判断は言いません。
3. **改造する**
   - 改造の指示を送ると、実装AIが部品の削除・差し替え・追加・移動と状態の変更という最小限の差分パッチを生成し、画面を書き換えます。触っていない部品は変わらないため、改修してもデザインが崩れません。
   - チャットのシステムメッセージ行に、`` `注文を確定する` の押したときの動きを `反応なし` から `注文完了` に変更 `` や `` `定期便` の最初の状態を `チェックあり` から `チェックなし` に変更 `` のように、どの部品・状態の何がどう変わったかがインラインコードバッジつきで1行ずつ表示されます。完了後もその行をクリックすると、スマホ画面内の該当部品へスクロールしてハイライト表示されます。
   - 適用後の画面は、描画できるか・購入完了のボタンと合計金額が残っているか・対象外の部品が書き換わっていないかを検証し、問題があれば直前のチェックポイントへ自動で戻します。
   - 改造の直後に、店長が売上の立場から一言反応します。
4. **お客さんの反応を見る**
   - レビューAIはこれまでの会話や改修意図を共有されない状態で、画面を実際に操作します。
   - ペルソナごとに設定された視界のぼかし・コントラスト低下・タップ位置のブレ・最大手数・許容待ち時間・細かい字を読むか・定期便やクーポンを望んでいるかなどの制約のもとでシミュレーションを実行し、コード側が結果を判定します。
   - 結果は4種類です。嫌な思いをせず買えた「達成」、買えたが途中でおとりを押した・罠に気づいて自分で外した・広告を閉じさせられた・欲しかった定期便やクーポンが消されていたなどの「買えたけど不満」、途中でやめた「離脱」、罠に気づかず買って「後悔」。選んだ3人全員が「達成」になるとクリアです。
   - Gemini は操作ログに基づく各ペルソナの感想生成のみを担い、改善方法は指示しません。感想はお客さん本人の発言としてチャットに表示され、店長も注文数や定期便の件数に反応します。
5. **トレードオフを判断して次の改善を回す**
   - まだ満足できていないお客さんに理由を聞いたり、売上が減って困っている店長の意見を聞いたりしながら、「ただ消す」のではなく「誰のためにどう整えて残すか」を判断して次の手直しへ進みます。
   - プレイ中の発言は、店長や顧客への質問（探索型）と画面の手直し指示（実行型）に分離して裏側で記録されます。指示文の具体的な対象・条件の有無を Cloud Natural Language API で抽出し、Vertex AI Text Embeddings によって指示の型（単純削除型・条件設計型・具体修正型・丸投げ型）を分類します。
   - 選んだ顧客層3人全員が満足してステージをクリアした瞬間のみ、LLMの主観採点ではなく「情報聞き出し回数・手直し指示回数・同じ部品への手戻り回数・初回成功率」と「どの指示への改善が決め手になったか」が実プロンプト引用つきでシステムログに表示されます。
   - 顧客層の選択・改造の判断履歴とプロンプトの行動テレメトリは、Cloud Firestore および BigQuery へ構造化保存されます。

## 3つのAIの役割分担

| 役割 | 入力 | 出力と制約 |
| :--- | :--- | :--- |
| **お助けエージェント（質問への回答）** | 現在のアプリ仕様・赤ペン囲み画像・対象部品ID・会話履歴・質問 | 仕様にある事実だけの短い回答と、そのまま押せる改造の指示の候補。判断や代弁はしない |
| **実装AI** | 改造の指示・現在のアプリ仕様・対象部品・会話履歴 | 最小限の差分操作の生成。適用後にサンドボックス検証を行い、失敗時は自動で戻す |
| **レビューAI** | 画面状態・制約変数下で実行した操作ログ。会話履歴は非共有 | コードが判定した達成・不満・離脱・後悔に沿った、ペルソナごとの感想生成 |

## ハッカソンでの拡張・カスタマイズ箇所

題材を差し替えるときは、[`src/shared/themes/coffeeBeans.ts`](src/shared/themes/coffeeBeans.ts) を参考に題材ファイルを1つ書き、[`src/shared/initialTheme.ts`](src/shared/initialTheme.ts) の `ACTIVE_THEME` を切り替えます。題材ファイルには次のものを書きます。

- 妨害要素を入れる前の画面（部品・状態・合計金額などの計算式）
- 妨害要素の候補と、毎回入れるもの・現実の使いにくさ・冗談の区別、難しさごとに選ぶ数
- 固定の問題（妨害要素を名前で並べたもの）と、既定で使う問題
- 店長のせりふと、お客さんの反応を見るたびに数える数字（定期便の件数など）
- 顧客層とペルソナ、各ペルソナの制約
- 冒頭で進行役が話す行と、実装AIへの題材特有の補足

画面の部品にはそれぞれ役割（本物のボタン、おとり、危険なボタン、必須の入力欄、関係ない項目、罠、合計、ポップアップ）を付けます。操作シミュレーターは部品のIDではなく役割を見て判定するため、題材を変えてもシミュレーターを書き換える必要はありません。

画面の見た目は描画側（[`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts) と [`src/client/style.css`](src/client/style.css)）が持ち、題材のデータは部品の種類と設定だけを書きます。

- 元のデザインは、専門店らしい温かみのある購入画面です。手順の表示、商品カード、選べるカード、金額の内訳、画面下に固定した合計と購入ボタンなどの部品で組み立てます。
- 妨害要素には `style.skin: 'intrusive'` を付けます。元のデザインの決まりを無視した、後から付け足したような見た目で描かれます。定期便の罠のように、気づかれにくくしたいものはあえて付けずに、元のデザインに溶け込ませます。
- 実装AIは部品単位の差分だけを返し、部品の種類と設定を変えるだけなので、改修してもデザインの品質は崩れません。

そのほかの主な拡張箇所は次のとおりです。

- [`src/shared/types.ts`](src/shared/types.ts)：UI部品の種類、役割、インタラクション挙動、アクションの型定義
- [`src/shared/appRuntime.ts`](src/shared/appRuntime.ts)：計算式・表示条件・アクションの実行規則。画面描画と操作シミュレーターで共有
- [`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts)：スマホ画面内でのコンポーネント描画とイベント発火ロジック
- [`src/shared/sandboxValidator.ts`](src/shared/sandboxValidator.ts)：単一HTMLサンドボックスの整合性検査と、部品の役割に基づく操作シミュレーション
- [`src/shared/promptTelemetry.ts`](src/shared/promptTelemetry.ts)：探索型・実行型の分離、指示の型分類、手戻り判定、クリア時の行動指標集計
- [`src/server/gemini.ts`](src/server/gemini.ts)：3つのAIのプロンプト設計、Structured Outputs スキーマ、発言の意図判定
- [`src/server/store.ts`](src/server/store.ts)：Cloud Natural Language API・Vertex AI Text Embeddings・Cloud Text-to-Speech・BigQuery・Cloud Firestore 連携

## 技術構成

- **フロントエンド**：TypeScript / Vite / HTML5 Canvas / Sandbox `iframe`
- **生成AI・音声**：`@google/genai` (Vertex AI / Gemini) によるマルチモーダル入力・Structured Outputs・Function Calling / Google Cloud Text-to-Speech API (11キャラクター別ボイス合成)
- **非LLM分析・テレメトリ基盤**：Google Cloud Natural Language API (エンティティ・感情抽出) / Vertex AI Text Embeddings (`text-multilingual-embedding-002` による指示クラスタ分類) / BigQuery Streaming Insert / Cloud Firestore
- **インフラ・セキュリティ**：Google Cloud Run / Firebase App Check
- **品質・衛生管理**：Node.js Test Runner / `scripts/check-hygiene.mjs` によるコミット・機密情報・パス混入検査

## セットアップ・起動方法

### 1. パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

`.env.example` を `.env.local` にコピーし、Gemini API キーまたは Google Cloud プロジェクトを設定します。AIを使う各ステップは接続設定が必須で、未設定の場合はエラーメッセージがチャットに表示されます。

```bash
cp .env.example .env.local
```

```env
GEMINI_API_KEY=your_gemini_api_key
```

### 3. 開発サーバーの起動

```bash
npm run dev
```

ブラウザで `http://localhost:5173` を開くとスタジオ画面が表示されます。

- 何も付けなければ、固定の問題（売上を伸ばしたい店長の画面）から始まります。題材に別の問題を足した場合は `?scenario=問題の名前` で選べます。
- `http://localhost:5173/?mode=random` を開くと、妨害要素の組み合わせが毎回ランダムになる練習用のモードになります。`&level=easy` のように `easy` `normal` `hard` を付けると壊れ方の多さを、`&seed=123` のように数字を付けると組み合わせの固定を選べます。
- `http://localhost:5173/?clean` を開くと、妨害要素を入れる前の画面を確認できます。題材のデザインを調整するときに使います。

### 4. テスト・ビルド・衛生チェック

```bash
npm test              # ユニットテスト・コミット衛生テストの実行（AIには接続しない）
npm run typecheck     # TypeScript 型チェック
npm run build         # 本番ビルド
npm run check:hygiene # 機密情報・ローカルパス混入・コミット規約チェック
```
