# yukid-df-hack｜粗悪なアプリの改修を通じてプロダクト思考を学ぶ開発スタジオ基盤

意図的に使いにくく作られたアプリを題材に、コード構文を直接書かずに、誰のために・何を優先し・何を捨てるかというプロダクトの意思決定サイクルを体験・検証するための開発スタジオ基盤です。

本リポジトリは、チーム内ハッカソンなどで他の開発者がベースとしてフォーク・改造することを前提に設計されています。改修対象となるアプリの初期仕様・顧客層・ペルソナの行動制約・妨害要素は題材ファイル1つにまとまっており、操作シミュレーターは部品の役割だけを見て判定するため、題材を差し替えて新しい課題アプリや評価環境を構築できます。

## サンプル題材：コーヒー豆の通販画面

初期状態では、商品の説明と注文フォームが1ページにまとまった単品通販の購入画面を題材にしています。

- **固定の問題「売上を伸ばしたい店長が付け足した画面」から始まります。** 反応しない注文ボタン、点滅する「残り2:59で売り切れ」、光る「今すぐ購入」のおとり、数秒後に出る会員登録の広告、最初からチェックの入った定期便の5つが入っています。
  - 注文ボタンを直すと、注文できる人と、定期便に気づかず注文して「後悔」する人が現れます。
  - 定期便を消すとほぼ全員が満足しますが、店長は売上が減って困ります。最後は確認画面を足すかどうかで、確実に買いたい人とさっと買いたい人がぶつかります。
- **依頼主の店長が登場します。** 冒頭で事情を話し、「どんなお客さんを一番大事にするか」を尋ねます。改造するたびに売上の立場から一言反応し、お客さんの反応を見るたびに注文数や定期便の件数をコードで数えて反応するので、お客さんとお店の板挟みを体験できます。
- **顧客層は「購入画面で何を求めているか」で分けています。** さっと買いたい人・確実に買いたい人・損をしたくない人の3つで、求めることがぶつかり合うため、誰を選ぶかが何を優先するかの判断になります。目が遠い・指が震える・画面が割れているといった違いは、各人の制約として持たせています。
- 練習用に、妨害要素の組み合わせを毎回ランダムにするモードもあります。妨害要素は、毎回必ず入るもの・現実の使いにくさ・冗談の3種類から選ばれ、壊れ方の多さを3段階から選べます。

| 難しさ | 妨害要素の数 | 冗談 | 向いている場面 |
| :--- | :--- | :--- | :--- |
| easy | 2〜3個 | なし | 初めての人、短い時間の体験会 |
| normal | 3〜5個 | 0〜1個 | 標準 |
| hard | 8〜9個 | 2個 | 慣れたチーム、何を捨てるかを強く迫りたいとき |

## 体験の流れ

1. **顧客層を選ぶ**
   - 依頼主の店長が事情を話したあと、進行役が「誰のために改造しますか」と尋ねます。選んだ顧客層の3人がお客さんとして来店し、レビュー担当になります。
2. **ダメ出しと質問**
   - スマートフォン実機プレビューの気になる部品を赤ペンで囲み、問題点や疑問を自然言語で送信します。
   - 赤ペンの軌跡座標とUI部品の矩形座標から対象コンポーネントを特定し、スクリーンショット画像とともにマルチモーダル入力としてAIへ渡します。
   - 質問には「お助けエージェント」が、画面の実際の仕様にある事実だけで短く答えます。誰が喜ぶか・困るかといった判断は言いません。
3. **改造する**
   - 改造の指示を送ると、改善案の選択肢を挟まずに、指示どおり画面を書き換えます。何を優先して何を捨てるかは、AIが先回りして示すのではなく、このあとのお客さんと店長の反応から学習者自身が気づく設計です。
   - 実装AIは画面全体を書き直さず、部品の削除・差し替え・追加・移動と状態の変更という差分だけを返します。触っていない部品は変わらないため、改修してもデザインが崩れません。
   - 適用後の画面は、描画できるか・購入完了のボタンと合計金額が残っているか・対象外の部品が書き換わっていないかを検証し、問題があれば直前のチェックポイントへ自動で戻します。
   - 改造の直後に、店長が売上の立場から一言反応します。
4. **お客さんの反応を見る**
   - レビューAIはこれまでの会話や改修意図を共有されない状態で、画面を実際に操作します。
   - ペルソナごとに設定された視界のぼかし・コントラスト低下・タップ位置のブレ・最大手数・許容待ち時間・細かい字を読むかどうかなどの制約のもとでシミュレーションを実行し、コード側が結果を判定します。
   - 結果は「達成」「離脱」に加え、完了はできたものの定期便などの罠に気づかなかった「後悔」の3種類です。
   - Gemini は操作ログに基づく各ペルソナの感想生成のみを担い、改善方法は指示しません。感想はお客さん本人の発言としてチャットに表示され、店長も注文数や定期便の件数に反応します。
5. **採否を決める**
   - 各ペルソナからのフィードバックに対して、人間が直す・反論して残す・保留の採否を決定し、次の改善サイクルへ進みます。理由は任意で添えられます。
   - 顧客層の選択・改造の指示・採否は、Gemini Function Calling を通じて判断履歴として記録されます。

## 3つのAIの役割分担

| 役割 | 入力 | 出力と制約 |
| :--- | :--- | :--- |
| **お助けエージェント（質問への回答）** | 現在のアプリ仕様・赤ペン囲み画像・対象部品ID・会話履歴・質問 | 仕様にある事実だけの短い回答と、そのまま押せる改造の指示の候補。判断や代弁はしない |
| **実装AI** | 改造の指示・現在のアプリ仕様・対象部品・会話履歴 | 最小限の差分操作の生成。適用後にサンドボックス検証を行い、失敗時は自動で戻す |
| **レビューAI** | 画面状態・制約変数下で実行した操作ログ。会話履歴は非共有 | コードが判定した達成・離脱・後悔に沿った、ペルソナごとの感想生成 |

## ハッカソンでの拡張・カスタマイズ箇所

題材を差し替えるときは、[`src/shared/themes/coffeeBeans.ts`](src/shared/themes/coffeeBeans.ts) を参考に題材ファイルを1つ書き、[`src/shared/initialTheme.ts`](src/shared/initialTheme.ts) の `ACTIVE_THEME` を切り替えます。題材ファイルには次のものを書きます。

- 妨害要素を入れる前の画面（部品・状態・合計金額などの計算式）
- 妨害要素の候補と、毎回入れるもの・現実の使いにくさ・冗談の区別、難しさごとに選ぶ数
- 固定の問題（妨害要素を名前で並べたもの）と、既定で使う問題
- 店長のせりふと、お客さんの反応を見るたびに数える数字（定期便の件数など）
- 顧客層とペルソナ、各ペルソナの制約
- 冒頭で進行役が話す行と、実装AIへの題材特有の補足

画面の部品にはそれぞれ役割（本物のボタン、おとり、危険なボタン、必須の入力欄、関係ない項目、罠、合計、ポップアップ）を付けます。操作シミュレーターは部品のIDではなく役割を見て判定するため、題材を変えてもシミュレーターを書き換える必要はありません。

画面の見た目は描画側（[`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts) と [`src/client/style.css`](src/client/style.css)）が持ち、題材のデータは部品の種類と設定だけを書きます。

- 元のデザインは、専門店らしい温かみのある購入画面です。手順の表示、商品カード、選べるカード、金額の内訳、画面下に固定した合計と購入ボタンなどの部品で組み立てます。
- 妨害要素には `style.skin: 'intrusive'` を付けます。元のデザインの決まりを無視した、後から付け足したような見た目で描かれます。定期便の罠のように、気づかれにくくしたいものはあえて付けずに、元のデザインに溶け込ませます。
- 実装AIは部品単位の差分だけを返し、部品の種類と設定を変えるだけなので、改修してもデザインの品質は崩れません。

そのほかの主な拡張箇所は次のとおりです。

- [`src/shared/types.ts`](src/shared/types.ts)：UI部品の種類、役割、インタラクション挙動、アクションの型定義
- [`src/shared/appRuntime.ts`](src/shared/appRuntime.ts)：計算式・表示条件・アクションの実行規則。画面描画と操作シミュレーターで共有
- [`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts)：スマホ画面内でのコンポーネント描画とイベント発火ロジック
- [`src/shared/sandboxValidator.ts`](src/shared/sandboxValidator.ts)：単一HTMLサンドボックスの整合性検査と、部品の役割に基づく操作シミュレーション
- [`src/server/gemini.ts`](src/server/gemini.ts)：3つのAIのプロンプト設計、Structured Outputs スキーマ、発言の意図判定

## 技術構成

- **フロントエンド**：TypeScript / Vite / HTML5 Canvas / Sandbox `iframe`
- **バックエンド**：Node.js HTTP Server / `@google/genai` によるマルチモーダル入力・Structured Outputs・Function Calling
- **インフラ・永続化**：Google Cloud Run / Cloud Firestore / Firebase App Check
- **品質・衛生管理**：Node.js Test Runner / `scripts/check-hygiene.mjs` によるコミット・機密情報・パス混入検査

## セットアップ・起動方法

### 1. パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

`.env.example` を `.env.local` にコピーし、Gemini API キーまたは Google Cloud プロジェクトを設定します。AIを使う各ステップは接続設定が必須で、未設定の場合はエラーメッセージがチャットに表示されます。

```bash
cp .env.example .env.local
```

```env
GEMINI_API_KEY=your_gemini_api_key
```

### 3. 開発サーバーの起動

```bash
npm run dev
```

ブラウザで `http://localhost:5173` を開くとスタジオ画面が表示されます。

- 何も付けなければ、固定の問題（売上を伸ばしたい店長の画面）から始まります。題材に別の問題を足した場合は `?scenario=問題の名前` で選べます。
- `http://localhost:5173/?mode=random` を開くと、妨害要素の組み合わせが毎回ランダムになる練習用のモードになります。`&level=easy` のように `easy` `normal` `hard` を付けると壊れ方の多さを、`&seed=123` のように数字を付けると組み合わせの固定を選べます。
- `http://localhost:5173/?clean` を開くと、妨害要素を入れる前の画面を確認できます。題材のデザインを調整するときに使います。

### 4. テスト・ビルド・衛生チェック

```bash
npm test              # ユニットテスト・コミット衛生テストの実行（AIには接続しない）
npm run typecheck     # TypeScript 型チェック
npm run build         # 本番ビルド
npm run check:hygiene # 機密情報・ローカルパス混入・コミット規約チェック
```
